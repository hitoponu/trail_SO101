## H-1 🔴 ベースの `j` / `l` が旋回する（**主目的**）

### 分かっていること

運動学のモデル自体は正しいです。純横移動 `vy` に対する 3 輪の周速度は

| 車輪 | ID | 周速度（`vy = +1` のとき） |
| --- | --- | --- |
| left | 7 | **+0.5** |
| back | 8 | **−1.0** |
| right | 9 | **+0.5** |

で、**平均がゼロ**（= 回転成分ゼロ）です。`test_kinematics.py` が
`m[BACK, 1] == -1.0` と「+y で後輪が負に回る」ことを固定しています。

したがって**コードのバグではなく、モデルと実機の対応付けのずれ**です。
`config/base.yaml` の 3 つのノブは**すべて既定値のまま**で、
`docs/agent/report.md` に実機合わせを実施した記録がありません。

```yaml
wheel_angle_offset_deg: -90.0
wheel_direction_signs: [1.0, 1.0, 1.0]
motor_ids: [7, 8, 9]
```

> ★ **Mac 側では判定できません。** モックの `/odom` は
> **送った指令値の積分**であって実測ではないので（`docs/internals.md`）、
> 何を確かめても自分の指令を読み返すだけです。
> 前回「strafe は動作している」と報告しましたが、**あれは誤りです**。

### ★ 取り違え 48 通りを総当たりして、原因を 1 つに絞りました

3 つのノブの誤りを全通り（並べ替え 6 × 符号 8）計算しました。

| ノブ | 横移動を旋回にできるか |
| --- | --- |
| `wheel_angle_offset_deg`（取付角） | **できない。** どの角度でも `wz = 0` |
| `motor_ids`（並べ替え） | **できない。** どの並べ替えでも `wz = 0` |
| **`wheel_direction_signs`（符号反転）** | **これだけができる** |

理由は単純です。`M` の第 3 列は 3 輪とも `+base_radius` なので、
**回転成分は 3 輪の速度の平均に比例**します。並べ替えは平均を変えず、
取付角のずれも 3 輪が 120° 等間隔なので平均を変えません。
**平均を変えられるのは符号反転だけ**です。

そして符号反転 7 通りのうち、**「前進は正常・横移動は旋回」に合うのは 1 つだけ**です。

| 反転している輪 | D1 純回転 | D2 前進 | D3 横移動 (+y) |
| --- | --- | --- | --- |
| **back(8)** | vx0.00 vy+0.17 **wz+0.33** | **vx+1.00 vy0.00 wz0.00** | vy−0.33 **wz+5.33** |
| left(7) | vx+0.14 vy−0.08 wz+0.33 | vy+0.58 wz+4.62 | vx+0.58 vy+0.67 wz−2.67 |
| right(9) | vx−0.14 vy−0.08 wz+0.33 | vy−0.58 wz−4.62 | vx−0.58 vy+0.67 wz−2.67 |
| left+right | vy−0.17 wz−0.33 | **vx−1.00**（逆走） | vy+0.33 wz−5.33 |
| left+back+right | wz−1.00 | vx−1.00（逆走） | **vy−1.00 wz0.00**（鏡像。旋回しない） |

**back(8) だけが「前進は完全に正常（vx+1.00, wz 0.00）」で、
かつ横移動がほぼ純粋な旋回（wz+5.33）になります。**

→ 予想される修正は**これ 1 行**です。

```yaml
wheel_direction_signs: [1.0, -1.0, 1.0]   # left, back, right
```

### やってほしいこと

**まず前進を確認してください。** ここで話が分かれます。

```bash
# コンテナ内。車輪を浮かせたまま

```

- **前進が正常なら** → 上の 1 行を `config/base.yaml` に入れて D3 を再確認
- **前進もおかしいなら** → 上の表は前提が崩れます。
  `docker/lekiwi_base_ros2/README.md` の「6.2」を **D1 → D2 → D3 の順に**
  最初から実施してください（順序を守ること。独立していません）

どちらの場合も、切り分けのために**運動学を迂回して 1 輪ずつ**回してください。
「どの物理車輪が left/back/right か」「どちら向きに回るか」を直接決められます。


## H-2 🟡 アーム: どのキーでも shoulder_lift が下がる（修正済みの確認）

### 何が起きていたか

`nudge_joint` が毎回 `/joint_states` の**実測値**を読み直し、そこに
ステップを足していました。保持力が弱い（`P=16`、トルク ≈ `P × 位置偏差`）ため
関節は重力で垂れ、**垂れた値が次の目標に焼き込まれて**いました。

自分が送った目標を保持してそこへ加算するように変えました。

### やってほしいこと

```bash
# コンテナ内
ros2 run lekiwi_examples teleop_keyboard
```

`1` `2` `3` `4` `5` を**1 回ずつ**押し、ステータス行を記録してください。

```
arm_shoulder_lift_joint 目標 -0.400 (実測 -0.520) rad
```

| 項目 | 見るもの |
| --- | --- |
| a | 各キーが**それぞれ別の関節**を動かすか |
| b | shoulder_lift が**押していないのに**下がり続けないか |
| c | **1 分間放置**して、目標と実測の差が何 rad まで開くか（★ `P=16` 問題の実測値。これが欲しい） |
| d | `Space` で実測値へ同期し直せるか |

## H-3 🟡 アーム: 押している間は震え、離すと動く（修正済みの確認）

### 何が起きていたか（★ モックでは再現しません）

キー 1 打ごとに軌道を投げていました。JTC は新しい軌道を受けるたび前の軌道を
捨てて**実測値から引き直します**（`open_loop_control` は既定 `false`。
実測で確認済み）。しかも始点速度に使う `/joint_states` の velocity は、
STS3215 の 1 量子が 0.077 rad/s に化ける信用できない値です（`CLAUDE.md`）。
端末のオートリピート（約 30Hz）でこれを毎回踏んでいました。

**モックは指令をそのまま状態として返す**（追従誤差ゼロ・velocity もきれい）ので、
この症状は構造的に出ません。**実機でしか確認できません。**

送信を 20Hz のタイマー 1 本に集約し、実際に送る目標が `arm_speed`
（既定 0.5 rad/s）で行き先へ寄るようにしました。

> ★ 途中で「最終点の速度を 0 以外にする」実装を試しましたが、JTC が
> `Velocity of last trajectory point ... is not zero` で**軌道を丸ごと拒否**し、
> アームがまったく動かなくなりました（モックで実測）。最終点の速度は 0 必須です。

### やってほしいこと

| 項目 | 見るもの |
| --- | --- |
| a | `2` を **3 秒押しっぱなし**にして、**滑らかに動き続けるか**（震えないか） |
| b | 押している間の実測の移動量 [rad]（★ `arm_speed` 0.5 rad/s に対して何割出るか） |
| c | **離してから止まるまでの追加移動量** [rad]（Mac のモックでは +0.195） |
| d | 別のキー（`3` `4`）でも同じか |

**もし震えが残る場合**、次の 2 つを試して結果を報告してください。
どちらも「原因が JTC の引き直しか」を切り分けるためのものです。

```bash

# ② 送信周期を落とす（既定 20.0）
```
